Overview

This change packages SuiteCloud CLI for Node.js as a Windows executable. Users can run suitecloud.exe directly without installing Node.js. The implementation first uses webpack to combine the CLI, SDK core, npm dependencies, command implementations, metadata, messages, and templates into one JavaScript file. It then embeds that bundle in a copy of the Node.js runtime using the Node.js SEA mechanism.

SuiteCloud source + SDK core + dependencies
↓ webpack
packages/node-cli/dist/suitecloud.js
↓ Node.js SEA blob + postject injection
packages/node-cli/dist/suitecloud.exe
Why source changes were necessary: the CLI on feature-ts-migration-devbase assumes that commands, JSON metadata, messages, templates, and package metadata are separate files in an installed npm package. Those files do not exist as normal filesystem entries inside a single executable, so CLI-owned resources had to become statically discoverable and embeddable.

Changes compared with feature-ts-migration-devbase

1. Single-file webpack bundle

File: packages/node-cli/webpack.single.config.js

This configuration creates the JavaScript input consumed by Node SEA.

  • target: 'node22' targets the same Node generation embedded in the executable.
  • splitChunks: false and runtimeChunk: false prevent additional output chunks.
  • LimitChunkCountPlugin({ maxChunks: 1 }) enforces one JavaScript file.
  • Node built-ins remain native because the embedded Node runtime provides them.
  • Asset rules import XML, template, and queried source files as JavaScript strings.
target: 'node22',
output: {
    path: path.resolve(__dirname, 'dist'),
    filename: 'suitecloud.js',
    clean: true,
},
optimization: {
    minimize: false,
    splitChunks: false,
    runtimeChunk: false,
}

File: packages/node-cli/webpack.config.js

A separate webpack configuration supports a conventional multi-file distribution by keeping CommonJS imports external and copying resources into dist. It is useful for normal distribution testing, but build:exe specifically uses webpack.single.config.js.

2. Static command generator registry

Files:

  • packages/node-cli/src/core/CommandGeneratorRegistry.js
  • packages/node-cli/src/core/CommandActionExecutor.js
  • packages/node-cli/src/core/CommandsMetadataService.js

The previous implementation loaded a generator from a path determined at runtime:

const commandGenerator = require(commandMetadata.generator);

Webpack cannot reliably include modules referenced only by a dynamic runtime path. The new registry statically requires every command generator, making all command implementations visible during compilation: 

module.exports = {
    'account:manageauth': require('../commands/account/manageauth/ManageAccountCommand'),
    'project:deploy': require('../commands/project/deploy/DeployCommand'),
    'proxy:start': require('../commands/proxy/start/ProxyStartCommand'),
    // Other commands omitted here
};

CommandActionExecutor now resolves a command through that registry:

const commandGenerator = commandGeneratorRegistry[commandMetadata.generator];

CommandsMetadataService also imports command metadata JSON statically and stores the command name as the registry key instead of constructing a source-tree path. structuredClone() prevents metadata merging from mutating cached JSON module exports.

3. Embedded JSON resources and package metadata

Files:

  • packages/node-cli/src/services/NodeTranslationService.js
  • packages/node-cli/src/CLI.js
  • packages/node-cli/src/core/CommandsMetadataService.js

Translation messages, command metadata, and package.json were previously located and read from disk. They are now imported with static require() calls, allowing webpack to embed them. This preserves CLI version output, compatible NetSuite version data, command definitions, help text, and translated messages. 

const messages = require('../../messages.json');
const configFile = require('../package.json');
const sdkCommandsMetadata = require('../metadata/SdkCommandsMetadata.json');

4. Embedded templates

Files:

  • packages/node-cli/src/templates/EmbeddedTemplates.js
  • packages/node-cli/src/templates/TemplateKeys.js
  • packages/node-cli/src/services/FileSystemService.js

The original implementation used require.resolve() to return paths to template files, which were then read from disk. The executable has no standalone template directory. Templates are now imported as source text: 

module.exports = {
    blankscript: require('./scripts/blankscript.js?source'),
    commerceextension: require('./objects/commerceextension.xml'),
};

FileSystemService.createFileFromTemplate() accepts both embedded multiline content and a traditional filesystem path. This maintains compatibility with existing callers while allowing file, object, and project creation from the executable.

5. Native loading of external suitecloud.config.js

File: packages/node-cli/src/core/extensibility/CLIConfigurationService.js

The project configuration is different from CLI-owned resources: it belongs to the user and must be loaded from the current project at runtime. The original dynamic call was transformed by webpack into a bundle-internal module lookup: 

this._cliConfig = require(cliConfigFile);

This caused the executable to report:

Cannot find module 'C:\work\NSNNetsuiteProjects\quarks\suitecloud.config.js'

The implementation now explicitly invokes Node's native CommonJS loader:

const { createRequire } = require('node:module');

this._cliConfig = createRequire(__filename)(cliConfigFile);

This bypasses webpack's module context, loads the absolute external path, and permits relative CommonJS imports inside the user's configuration file.

6. Node SEA executable packaging

File: packages/node-cli/scripts/build-sea.js

The SEA builder follows these steps:

  1. Create a temporary SEA configuration whose main script is dist/suitecloud.js.
  2. Run the current Node executable with --experimental-sea-config to generate a preparation blob.
  3. Copy process.execPath to dist/suitecloud.exe.
  4. Use postject to inject the blob as NODE_SEA_BLOB.
  5. Set the Node SEA sentinel fuse during injection.
  6. Delete the temporary SEA configuration and blob.
runNode(['--experimental-sea-config', seaConfigPath]);
copyFileSync(process.execPath, executablePath);
await inject(executablePath, 'NODE_SEA_BLOB', readFileSync(seaBlobPath), {
    sentinelFuse: 'NODE_SEA_FUSE_fce680ab2cc467b6e072b8b5df1996b2',
});

Using process.execPath for both blob generation and the copied runtime ensures their Node versions match. Snapshots and code cache are disabled to keep the build straightforward and avoid cache compatibility issues.

7. Build dependencies and scripts

Files:

  • package.json
  • packages/node-cli/package.json
  • package-lock.json
DependencyPurpose
webpackBundles CLI code, SDK core, npm dependencies, metadata, and assets.
webpack-cliRuns webpack through npm scripts.
postjectInjects the SEA preparation blob into the Windows PE executable.
copy-webpack-pluginCopies files for the conventional multi-file webpack distribution; not used by the SEA configuration itself.

CLI workspace scripts:

"build": "webpack --config webpack.config.js",
"build:single": "webpack --config webpack.single.config.js",
"build:exe": "npm run build:single && node scripts/build-sea.js"

Root orchestration script:

"build:exe": "npm run build && npm run build:exe --workspace @oracle/suitecloud-cli"

The order is important: SDK core TypeScript is compiled first, then the CLI and compiled SDK core are bundled, and finally the bundle is injected into the executable.

Distribution considerations

Code signing: SEA injection modifies the copied Node executable and invalidates the digital signature inherited from node.exe. The build may display warning: The signature seems corrupted!. This is expected. Code-sign the final suitecloud.exe after injection and before distribution.
  • The executable is platform-specific. The current builder intentionally creates a Windows .exe.
  • End users do not need Node.js installed.
  • Java-backed SuiteCloud commands still require Oracle JDK 17 or 21 and the SuiteCloud SDK JAR.
  • The executable should be rebuilt with the supported Node 22 LTS release used for distribution.
  • Normal release validation, security scanning, license review, and signing processes still apply.

Conclusion

Compared with feature-ts-migration-devbase, this implementation changes the CLI from an npm-package runtime that depends on a source/resources directory into a bundle-safe runtime. CLI-owned modules and assets are statically embedded, while user-owned project configuration remains dynamically loadable through Node's native module loader. The resulting suitecloud.exe embeds Node.js and has been verified against an external SuiteCloud project.
