Executive summary

The original CLI behaved like a normal installed npm package. It discovered command modules from runtime paths, read metadata and templates from the filesystem, and loaded project configuration with a dynamic require(). Those patterns work when all source files remain beside the entry point, but they prevent webpack from determining everything that must be included in a single bundle.

The webpack-compatible implementation separates resources into two groups. CLI-owned modules and resources are made statically visible so webpack can include them. User-owned resources, particularly suitecloud.config.js, remain external and are deliberately loaded with Node's native module loader. Two webpack configurations are provided: a conventional multi-file distribution and a true single-file bundle that can also be embedded into a Node.js Single Executable Application (SEA).

Why the source had to change

Original runtime patternWebpack problemImplemented solution
Dynamic command path passed to require() The dependency graph does not contain a concrete module path, so commands can be omitted. A registry contains a static import for every command and loads each command lazily.
Metadata and messages read from paths on disk Files inside a single bundle do not exist at their old source-tree paths. JSON is imported statically and becomes part of the bundle.
require.resolve() returns template paths A single-file bundle cannot expose those templates as ordinary adjacent files. Template contents are imported with webpack asset modules and passed as strings.
Dynamic loading of a user's suitecloud.config.js Webpack may reinterpret the dynamic call as a bundle-internal module lookup. createRequire() explicitly delegates to Node's native CommonJS loader.
Potentially multiple output chunks Node SEA accepts one main JavaScript file. Chunk splitting is disabled and the chunk count is limited to one.

This order matters because webpack consumes @oracle/suitecloud-sdk-core through its compiled build entry point. The lockfile was regenerated after merging dev, retaining the newer Jest and runtime dependency versions together with the webpack toolchain.

2. Conventional multi-file webpack distribution

packages/node-cli/webpack.config.js

This configuration produces a normal package-like directory. It bundles only the executable entry and preserves native CommonJS resolution for the remaining files. The source tree, messages, resources, package manifest, postinstall script, and README are copied to dist.

  • target: 'node' emits code for Node.js.
  • output.filename: 'src/suitecloud.js' preserves the installed package layout.
  • externalsPresets.node keeps Node built-ins external.
  • The custom externals callback leaves imports as CommonJS requests, except for the entry itself.
  • CopyWebpackPlugin reconstructs the files needed by the normal package runtime.
  • BannerPlugin preserves the #!/usr/bin/env node launcher.
  • Minification is disabled and source maps are enabled to keep the output debuggable.
Purpose: this mode validates that a webpack-generated distribution still behaves like the npm package. It is not the input used by the SEA builder.

3. Single-file webpack bundle

packages/node-cli/webpack.single.config.js

This configuration emits packages/node-cli/dist/suitecloud.js, which contains the CLI, SDK core, dependencies, metadata, messages, and supported templates.

  • target: 'node22' matches the Node generation used by the SEA executable.
  • splitChunks: false and runtimeChunk: false prevent secondary files.
  • LimitChunkCountPlugin({ maxChunks: 1 }) enforces the single-output contract.
  • devtool: false avoids a separate source-map artifact.
  • asset/source converts queried source files, XML, and template files into JavaScript strings.
  • The Node shebang is added to the one entry bundle.
module: {
    rules: [
        { resourceQuery: /source/, type: 'asset/source' },
        { test: /[\\/]templates[\\/].*\.(?:xml|template)$/, type: 'asset/source' }
    ]
},
plugins: [
    new webpack.optimize.LimitChunkCountPlugin({ maxChunks: 1 })
]

4. Static, lazy command registry

packages/node-cli/src/core/CommandGeneratorRegistry.js, packages/node-cli/src/core/CommandActionExecutor.js, and packages/node-cli/src/core/CommandsMetadataService.js

The old executor attempted to load a path supplied by metadata:

const commandGenerator = require(commandMetadata.generator);

Because the path is not a literal, webpack cannot reliably identify the command modules. The registry now contains literal require() calls, while a small wrapper defers evaluation until the selected command is executed: 

const lazy = (loadCommand) => ({
    create: (...args) => loadCommand().create(...args),
});

module.exports = {
    'config:import': lazy(() => require('../commands/config/import/ImportConfigurationCommand')),
    'project:deploy': lazy(() => require('../commands/project/deploy/DeployCommand')),
    // Every other supported command is registered in the same way.
};

The lazy wrapper is important after the dev merge. It keeps every dependency statically visible to webpack without eagerly initializing commands that use ESM-only interactive code or raw template imports. The registry also includes the new config:import command introduced on dev.

CommandActionExecutor uses the metadata's command name as the registry key:

const commandGenerator = commandGeneratorRegistry[commandMetadata.generator];

5. Static command metadata

packages/node-cli/src/core/CommandsMetadataService.js

The metadata service no longer constructs paths and reads JSON with the filesystem service. All four metadata files are imported with literal paths, allowing webpack to include them in its graph: 

const sdkCommandsMetadata = require('../metadata/SdkCommandsMetadata.json');
const sdkCommandsMetadataPatch = require('../metadata/SdkCommandsMetadataPatch.json');
const nodeCommandsMetadata = require('../metadata/NodeCommandsMetadata.json');
const commandGeneratorsMetadata = require('../metadata/CommandGenerators.json');

Generator metadata is converted from a filesystem path into a stable command-name key. The imported objects are cloned before merging because Node caches JSON modules; without cloning, metadata initialization could mutate the shared module export.

6. Static messages and package metadata

packages/node-cli/src/services/NodeTranslationService.js, packages/node-cli/src/CLI.js, and packages/node-cli/src/ExecutionEnvironmentContext.js

The CLI's messages and package metadata are owned by the application, so they are imported rather than rediscovered from __dirname or require.main.filename. This lets webpack embed the values needed for error messages, --version, NetSuite compatibility information, the SDK filename, and telemetry. 

const messages = require('../../messages.json');
const configFile = require('../package.json');
const { nsCompatibleVersion, sdkFilename } = require('../package.json');

7. Embedded templates and dual-mode file creation

packages/node-cli/src/templates/EmbeddedTemplates.js, packages/node-cli/src/templates/TemplateKeys.js, and packages/node-cli/src/services/FileSystemService.js

Templates previously flowed through the application as filesystem paths returned by require.resolve(). The single-file build instead imports their contents. The ?source query selects the asset/source rule for JavaScript that must be treated as text, while XML under a templates directory is covered by the file rule. 

module.exports = {
    blankscript: require('./scripts/blankscript.js?source'),
    commerceextension: require('./objects/commerceextension.xml'),
};

TemplateKeys exposes the imported strings. FileSystemService.createFileFromTemplate() now accepts either multiline template content or a traditional path. This preserves compatibility with non-bundled callers while allowing the single bundle to create files without extracting its internal templates.

8. Native loading for external project configuration

packages/node-cli/src/core/extensibility/CLIConfigurationService.js

Unlike messages and templates, suitecloud.config.js belongs to the user's project and cannot be embedded at build time. The implementation uses Node's native loader explicitly: 

const { createRequire } = require('node:module');

this._cliConfig = createRequire(__filename)(cliConfigFile);

This prevents webpack from turning the absolute runtime path into a bundle-internal lookup and preserves relative CommonJS imports made by the user's configuration file.

9. Node SEA executable packaging

packages/node-cli/scripts/build-sea.js

SEA packaging is downstream of webpack rather than a requirement for webpack itself. It consumes the output of build:single and creates a native executable through these steps:

  1. Write a temporary SEA configuration that names dist/suitecloud.js as its main script.
  2. Run the current Node binary with --experimental-sea-config to generate a blob.
  3. Copy process.execPath to the platform-appropriate output name.
  4. On macOS, remove the copied binary's signature before injection.
  5. Inject NODE_SEA_BLOB with postject and the Node SEA sentinel fuse.
  6. Set executable permissions on non-Windows platforms and apply an ad-hoc macOS signature.
  7. Remove the temporary configuration and blob in a finally block.

The builder rejects unsupported platforms and accidental cross-platform requests. SEA executables must be created natively on their target operating system. Using process.execPath for both blob generation and the copied runtime guarantees compatible Node versions.

Maintenance rules

  1. When adding a command to CommandGenerators.json, add the same command key and a literal lazy import to CommandGeneratorRegistry.js.
  2. Do not replace static CLI-owned JSON imports with computed filesystem paths.
  3. When adding a bundled template type, add an asset/source rule if the existing rules do not match it.
  4. Keep user-owned configuration external and load it through Node's native module system.
  5. Compile SDK core before invoking the CLI webpack build.
  6. Run both webpack modes; they intentionally exercise different module-resolution models.
  7. After changing dependencies, regenerate and commit the root lockfile.
  8. Build SEA artifacts on the target platform and sign the final executable after blob injection.

Conclusion

Webpack compatibility was achieved by making the application's internal dependency graph explicit while preserving true runtime dependencies as external. Static JSON imports, the lazy command registry, embedded templates, and native external configuration loading are the essential runtime changes. The two webpack configurations and npm scripts provide repeatable multi-file and single-file outputs, while the optional SEA stage turns the single bundle into a platform-native executable.
