# Domain reference

Support the user’s requested analysis and authorized actions through available, supported tools. Establish the target, intended effect and required business inputs before acting; reuse authorization already given for that exact scope. Tool availability and source examples do not grant authorization. Preserve business validation, actual host approvals and account permissions. If the operation or required procedure is unavailable, explain the specific gap and provide a useful proposal without claiming execution.

# v12 source authority and documented adaptations

The four newly supplied Markdown specifications are the primary business workflow for v11.
Their terminology, sequence, visual sections and intended analysis take priority over v10.
The stable four package identifiers are retained; the names supplied in source frontmatter are activation aliases, not new entrypoints.

## Resolution order
1. Actual host permissions/safety, explicit current-user intent, confidentiality, truthful evidence and necessary connector protocol safeguards.
2. The [v12 scope/output overrides](scope-and-output.md), then the applicable supplied specification integrated into that skill's SKILL.md.
3. A narrowly selected v10 reference ONLY for a concrete unanswered requirement. Record a fallback reason and the reference used. Do not preload the old entrypoint, core manual, broad investigation gates, or all native Indicator definitions.
4. If neither source nor fallback resolves a fact, definition, transport or permission, disclose the exact gap. Do not invent it.

The original connector baseline is retained unchanged as an operating contract with the documented integration evolution.
For a requested action, establish its scope, authorization, supported tool schema and business prerequisites; execute only when these are satisfied and verify the resulting state. Keep proposals distinct from completed actions.

## Intentional business changes from v10
- Operations: the supplied allocation-led six-section staffing analysis replaces plannedwork-only calculations in that primary workflow.
  Title-similarity placement becomes a labeled first-pass suggestion; it is not verified skills/certification or an authorized assignment.
  Dated plannedwork/calendar analysis is a targeted fallback when actual availability cannot be established or is requested explicitly.
- Portfolio: retain the supplied hours/financial analysis, but v12 resolves PM scope automatically and includes all accessible scoped projects. Past-end is a visible category, never a default exclusion.
- Risk: discover suitable risk-focused saved searches before derived analysis. The old mandatory native-first/full-investigation
  start is not automatically injected into this source-led workflow. Native Indicator rules themselves remain unchanged and
  apply when native results are used, requested, or needed to resolve a gap. Never relabel custom data as a native indicator.
- Financial: v12 uses all accessible scoped projects; calendar YTD remains the period default, not fiscal YTD.
  Use the supplied report-purpose sequence and dedicated project reports when enabled and compatible.
- Primary layouts replace the adaptive v10 default for these four supplied workflows; v10 visuals remain fallbacks,
  not a requirement to replace the supplied design. SOW and uncovered billing/compliance work remain targeted extensions.
- Analysis alone does not authorize financial or configuration changes. For requested changes, follow the shared action contract: establish exact scope, authorization, supported capability and business prerequisites, then verify the outcome. No Statement of Work (SOW) execution runbook is packaged.

## Explicit exceptions to the supplied text (not silent corrections)
E01 — Tool names and fields: source tool aliases, field names and queries are technical candidates, not capability guarantees.
Use actual discovered schemas. Metadata-first, explicit columns and complete bounded paging replace SELECT * probes and a
thirty-row recent-project shortcut. Named-project resolution must be scoped and exact before final selection. A name search
can propose candidates; ambiguity never grants identity. Do not retrieve personal emails unnecessarily.

E02 — Source mappings: standard preserves report-purpose suggestions, resolving report identifiers through the returned catalogue.
No tenant saved-search IDs, tenant prefixes or sample business records are distributed. No-static-mapping keeps the same
workflow but stores no report-ID/field/query lookup table; it resolves those bindings at runtime. This documented variant
exception avoids restoring the mappings the user previously removed.

E03 — Missing is not zero: the financial source's cost-or-zero profit formula, null-aging-means-none shortcut, cost bar zeros,
and zero-denominator margin cannot substantiate confirmed figures. Its own no-fabrication/missing-data rules take precedence.
Unknown cost -> unknown profit/margin; empty aging -> no overdue balances ONLY after successful scope/period-complete evidence
establishes a genuine empty population. No cost-capture reason is inferred from missing access alone.

E04 — Labels: recognized revenue is not invoiced revenue; cost from time entries alone is labor cost, not all project cost.
A selected revenue field is not booked contract value without a verified definition. Use actual source labels and declare
any proxy. A supplied numeric threshold is a local descriptive policy, not a native NetSuite severity or causal conclusion.
Keep cost/recognized revenue/billing/commitments/cash separate and never aggregate different currency/book/period bases.

E05 — Time and populations: a past calculated end date is not proof of closed status; retain 'past scheduled end' as a visible category under v12, not a default exclusion. Missing end does not prove no tasks: obtain task count. Unresolved assignees can be vendors or unavailable
records, not automatically generic. Missing allocations do not prove unassigned tasks or actual free capacity. Keep candidate
template records separate unless positive metadata confirms template status; names/prefixes/null status alone cannot prove it.

E06 — Allocation interpretation: retain the supplied peak concurrent allocation analysis. Verify allocation units and common base,
duplicate/parent-child semantics, dates and additivity before calling it confirmed load. Otherwise show a candidate overlap.
Do not distribute fixed-hour totals or infer spare working hours from percentages. Zero current allocation is 'no recorded
commitment', pending task/calendar/leave and competing-work checks; inferred bench is not confirmed free. Missing allocation
metadata means unavailable, not 'none found'.

E07 — Risk meaning: late plus over-hours is co-occurrence, not confirmed scope cause or automatic severity escalation.
Investigate and label any interpretation separately. A flagged search is a source-defined flag, not an invented universal risk
score. Placeholder detection uses verified entity type/configuration, not an account naming convention. Retain scope/coverage
for every search and requested answer. A 132-control matrix is not required.

E08 — Template security/portability: keep the supplied financial/staffing structure, colors and sections, but remove remote
fonts/scripts; replace raw innerHTML data insertion with escaped server-side rendering and safe DOM interaction. Use a local
CSS bar chart instead of the financial template's external Chart.js. React/Recharts/present_files are not assumed to exist.
Use real host delivery. Add source/coverage footers to staffing because their absence would drop required evidence.
Do not populate template example numbers. Focus/case cards are 'up to' the requested count, not padding with invented cases.
