# Retrieval

Use the connector's current schema; the field names below are required semantics, not assumed tool arguments.

## Expiry, accrual limits, and idle balances

Use `timeoffchange` as the core source. Retrieve `id`, employee internal ID, time-off type ID, change type, applied date, signed amount, description, accrual rate, and linked request when available. Include `ACCRUAL`, `USAGE`, `CARRYOVER`, `YEAR_END_EXPIRY`, `CARRYOVER_EXPIRY`, `MANUAL_INCREASE`, and `MANUAL_DECREASE`.

Time-Off Change amounts are hours. Use `timeoffchange` for skill retrieval; report -306 remains a valid human UI cross-check but is not the query source because it identifies employees by display name. Never match employees by display name or relabel amounts from a type's `incrementunit`.

For SuiteQL, group by raw IDs rather than `BUILTIN.DF()` expressions. Verify each required field, relation and status with the current SuiteQL metadata interface before querying. Do not probe uncertain columns; missing essential schema blocks the dependent query. A REST-only metadata failure does not establish a SuiteQL denial, but an underlying data denial remains binding. Use stable unique ordering and a supported page size, retrieving every relevant page before population counts or denominators; record partial coverage when a limit prevents completion.

Exclude active employees without a time-off plan from expiry, idle-balance, and low-use populations and denominators. State the excluded count without naming them. Do not mention inactive employees by default; for an explicitly historical question, include people active in the historical population separately when the connector can establish that basis.

Read each active employee's `timeoffplan` and `startdatetimeoffcalc` individually, then retrieve that plan's `startmonth` and enrolled time-off types. Never infer plan membership from supervisor, department, colleagues, other organizational attributes, or the Time-Off Changes returned. Analyze only types enrolled for that employee's own plan. If the enrollment relationship cannot be retrieved, do not produce a type-specific portfolio or group conclusion that could include an ineligible type; state the precise limitation.

When an entitlement, carryover cap, or idle-balance threshold is configured in days but the comparison must be in hours, retrieve the employee's assigned work calendar and its `workhoursperday`. Convert the source day amount with that employee's value; never infer a day length from another employee's plan or transaction figures. If no calendar is available and an assumption is necessary to answer the request, label the assumed hours-per-day value and its effect on the threshold. For a fixed-amount plan, derive the threshold from the plan's annual entitlement and configurable share, not an employee's balance or accrual history; that plan threshold is shared by everyone on the plan. For an hourly plan, derive the threshold separately from each employee's posted accruals to date. State the threshold and its derivation with an employee-level comparison.

For each plan cycle, begin the Time-Off Change window on the first day of the entitlement period containing the analysis date or selected event. Do not use a rolling “today” lookback for a derived balance. Include scheduled future `ACCRUAL` rows through the analysis horizon for expiry, accrual-limit, and applicable fixed-plan idle-balance analysis, even when the employee has no current balance. When plans have different `startmonth` values, partition employees by cycle and run one retrieval per cycle; never apply the earliest start month as a shared window. Present each entitlement cycle as a separate list with its own period basis.

For forward-looking expiry, retrieve the next future `YEAR_END_EXPIRY` event and, where the employee's rules make it applicable, the related future `CARRYOVER_EXPIRY` event per enrolled type. Treat those as separate events. Determine the next upcoming applicable event chronologically for the default answer. Retain a later applicable carryover-expiry event only to state its date and conditional future consequence; never project or output its amount, and never add it to the next-event result. Start the retrieval at the entitlement-period boundary and extend it through both relevant event dates, plus the next day after each event to capture carryover. Use `startdatetimeoffcalc` to assess a source absence of expiry: balance accrued before that calculation start date is outside expiry calculation and is not a retrieval failure or time at risk. Past events are used only for an explicitly retrospective request.

Retrieve applicable rules for the employee's own plan to determine the applicability and timing of separate expiry events, or when needed for idle-balance basis, an accessible plan-setting explanation, or an anomaly, conflict, or data-quality question. For dual-event expiry analysis, retrieve `allowcarryover`, `maximumcarryover`, `expireunusedcarryover`, and `carryoverexpirymonth` when exposed. Rule data does not block the year-end expiry analysis; if unavailable, preserve the verified event result and limit only the dependent carryover-expiry, idle-balance, or explanation branch. Use `startdatetimeoffcalc`, not `hiredate`, when an accessible rule check depends on tenure.

For an individual balance explanation whose posted accruals appear lower than the plan rules would otherwise suggest, retrieve the employee's accessible `systemnote` history for plan assignment and calculation-start changes. Restrict employee notes by both the employee `recordid` and `recordtypeid = -9`; `recordid` alone can match another record type. Retrieve `date`, `field`, `oldvalue`, and `newvalue`, and use the plan-assignment (`EMPLOYEE.KTIMEOFFPLAN`) and calculation-start (`EMPLOYEE.DTIMEOFFCALCULATIONSTART`) fields when exposed. If plan assignment occurred after the calculation start date, explain that accruals begin at assignment and do not backfill; state both dates and the mechanism without judgment.

## Current liability hours

Resolve the current Time-Off Balance Summary report identity and parameter schema; -307 is a source reference, not proof of availability. Use this report only when the user asks for current outstanding time-off balances or liability hours. This analysis is separate from future expiry exposure. Run the report from the first day of each entitlement period through today, and use its `Balance` column and report-provided totals. Do not recreate a liability figure from `timeoffchange` or manually sum report detail rows.

Partition the population by plan `startmonth` and run report -307 separately for every entitlement cycle. State the period basis with each result. If the connector makes a report-level combined total available, use it; otherwise do not manually create a cross-cycle grand total. Retrieve `Carried Over`, `Earned`, `Used`, `Carryover Expiry`, and `Balance` when exposed. If the report or its `Balance` field is unavailable, mark only the current-liability branch unavailable and do not substitute expiry or carryover figures.

For a requested contact-priority ranking, use the already retrieved next-event expiry and next-day carryover data to identify the primary type by aggregate net hours at risk for each plan. This selection retrieval is not a current-liability answer: do not query report -307 or use a current balance to select, include, or exclude employees. Do not use a type name to infer priority, and do not return a ranking only when the required upcoming-expiry data is unavailable.

## Coverage

Use Time-Off Requests to establish approved and pending request scope, and use `timeoffchange` records of type `USAGE` for the approved absence dates. Include every time-off type by default; never narrow coverage to an expiry-primary or other selected type unless the user explicitly asks for that type. Pending requests create no `USAGE` entry, so retrieve them separately using an inclusion filter with employee ID, requested dates, status, and `creationdate` when available. A rejected or canceled request must not count as absence. Retrieve request IDs only for an authorized, requested individual drill-down.

For approved coverage, retrieve `USAGE` changes in the requested date boundary for the eligible approved-request population. Use each change's applied date, not a request start or end date; this relies on NetSuite's work-calendar treatment and avoids creating absence on a non-working day. The requested range is a search boundary: deduplicate each employee only within a same-date overlap period, never across the entire range. Pending requests use their requested spans because they have no `USAGE` record.

For grouping, retrieve the active roster with employee ID, time-off plan presence, and direct supervisor; retrieve department only when it is needed as context or to honor the user's scope. A supervisor group means active direct reports only and excludes the supervisor. Analyze overlap by supervisor team only. Job title and sub-tree are not analysis grouping dimensions.
