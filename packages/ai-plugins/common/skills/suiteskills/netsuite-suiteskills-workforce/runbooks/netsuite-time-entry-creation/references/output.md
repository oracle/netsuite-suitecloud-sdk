# Chat output

Keep draft, exact final review, and persisted result distinct. Use Markdown in the conversation. Never generate an HTML dashboard, JSON handoff, or local preview file. Keep connector JSON and source IDs in audit context, while showing readable names and exact IDs where decisions depend on them.

## Draft and every redraw

Group rows by local date. Use a stable row ID and a **unique Description** in the current table. Make Description recognizable enough that “the Atlas discovery entry” selects exactly one row. If two descriptions collide, add a short factual distinction such as date or activity source. Preserve row IDs through edits; redraw **all current rows** after an edit, even when the edited row remains Needs clarification.

These are synthetic examples, not account values. Keep the individual relevant field columns shown in the specification. Add Billing Class, payroll, workplace, price/rate, timesheet, or custom columns when the live contract makes them relevant. For a very wide table, use a per-row details table keyed by ID for the conditional fields; do not collapse Department, Class, Location, or other relevant fields into one summary cell. Every row still identifies its missing fact and Location status. Show source/provenance and account/time zone once near the table. Approval Status is a predicted/unknown initial state until readback; do not present it as persisted.

Below the table state proposed total; existing logged total for the period when covered; duplicate, overlap, buffer, and rounding adjustments; assumptions, exclusions, unknown coverage, and verified blockers. Say that no records were created. Ask the user to select by ID or unique Description, supply missing facts, or cancel. Show which rows remain selected across redraws. Allow selection/edit of Needs clarification rows; request their missing facts and keep them selected until Ready or explicitly deselected. Never imply those rows can yet be saved.

For a finite unresolved field, phrase a short question so the host can present **native chat interactive multiple-choice** input when available. Example prompts: “For A2, should this time be billable: Yes or No?” and “For A2, which Location applies: US-BDR (7) [candidate] or Manila (9) [candidate]?” These are questions in the chat UI, not buttons inside the Markdown table. Native controls may not appear; do not promise that they will. In that case, show a numbered text fallback: for Billable, “1. Yes; 2. No”; for Location, “1. US-BDR (7) — candidate; 2. Manila (9) — candidate.” Accept a typed number, label, or Location ID. Offer only current, permitted, readable, context-scoped candidates, and never auto-select one. A typed answer remains valid even when native options appear. After a clicked or typed choice, validate and redraw the entire table with updated readiness. Do not interpret any choice as Save or ask Save before the separate exact final review.

## Fixed final review

Only after **every selected row** is Ready, present **one rendered Markdown table** grouped by date, **even when exactly one row is selected**. Bullets, prose, a key-value list, or a compact “exact fields” cell are insufficient for final Save confirmation. Give each relevant payload field its own column, name the connector field in the header, and show the exact value/ID in the cell. Retain ID and unique Description so the user can match the draft. If a selected row still needs clarification or is Ineligible, ask for its missing facts or explicit deselection and redraw; do not omit it from a Save review.

This is a synthetic example. Include only applicable field columns; if a conditional payroll, billing class, price/rate, or custom field applies, add its own column or a **keyed per-row Markdown field/value table** showing exact connector name, value/ID, and verification. Do not hide fields in a semicolon list or move the only table into a code fence. Mark administrator-provided IDs **unverified in the same row** (for example `item` 280), distinguish account-verified values from candidates, and state that NetSuite may reject an unverified value. Show relevant **not sent** states, especially Location and timesheet link, and requiredness/writability gaps. Near the table include account, target and authenticated identity provenance, source, duplicate intent, existing/proposed totals, coverage, adjustments, and rows explicitly not selected.

After the table and contextual notes, ask separately: **“Save these exact rows, or Cancel?”** A row selection, clarification, or initial “log time” message is not this decision. A material edit requires a new table review and a fresh Save.

## Results after Save

Return the **same field columns as the draft**, with an added Result column. For saved rows, use values from independent record readback, not the proposed payload. For rejected or unattempted rows, retain their **latest proposed values** in those columns, clearly label them unsaved, and never imply they persisted. Include every selected row, including rejected and unattempted rows after a paused batch, and keep the same ID/Description.

In real results, add the same conditional columns used in the draft, including timesheet association, billing class, payroll, rate, or custom fields. Report saved/failed/uncertain counts; verified incremental total; account-side adjustments; and IDs already created so a retry does not duplicate them. A create response without record readback is **unverified**, not verified saved. If a required-field rejection occurs, identify the failed row and all remaining unattempted rows, then redraw the corrected draft/final review before any retry.
