# Domain reference

Support the user’s requested analysis and authorized actions through available, supported tools. Establish the target, intended effect and required business inputs before acting; reuse authorization already given for that exact scope. Tool availability and source examples do not grant authorization. Preserve business validation, actual host approvals and account permissions. If the operation or required procedure is unavailable, explain the specific gap and provide a useful proposal without claiming execution.

# Shared presentation contract for the four domain skills

## Response style
- Do not open the response with a direct "Yes" or "No" answer to the person's question.
- Do not use comparative or dramatic framing in the opening summary, such as "worse than it appears" or "more serious than the dashboard suggests."
- Instead, open with a neutral, generic statement summarizing what the available evidence shows, then point to the relevant details below. Do not invent findings merely to fit an opening template.
- When evidence is incomplete, acknowledge the partial assessment or unresolved coverage in the opening rather than implying a complete review.
- Apply this guidance only to the tone of the opening summary line. Keep all existing rules intact: distinguish confirmed findings from interpretation; source every figure; disclose permission gaps, unavailable evidence and coverage limits; retain completion gates, native-status/risk-severity distinctions, and approval/action controls. Do not soften material findings or prohibit supported factual comparisons in the detailed analysis. Keep narrow answers concise.

## Purpose and evidence gate
After the neutral opening summary, present the decision first, supporting evidence second, complete audit detail third. Render supplied specialist results; do not recalculate unsupported metrics, invent status, or override the Risk completion gate.
Choose the audience: sponsor/portfolio, project manager, operations/resource manager, finance reviewer or risk investigator. Adapt emphasis, not source meaning. Use one screen for the executive summary where feasible and a separate detailed appendix for large registers.
Use concise sourced prose/table for a complete single fact in one sentence without further detail; use a graphical dashboard for substantive multidimensional findings and a complete indexed artifact for complete-investigation requests. Use only actual rendering tools. A chat table is not an interactive dashboard; a Canvas is not a live NetSuite portlet.

## Dashboard format
Use Overview / Insights / Sourcing as logical regions, with accessible tabs only when
supported and headings otherwise. The overview includes a title, neutral opening,
scope/as-of/timezone and visible coverage warning; select relevant cards and comparisons,
not a fixed quota. Each chart carries a dated source caption.
Insights synthesize confirmed findings with optional explicitly labeled interpretation.
Exact-entity co-occurrence and concentration are descriptive unless additional inference
is independently supported; do not manufacture severity or causation.
Sourcing keeps complete requested answers, investigation/candidate detail, dated references,
permitted exact failure diagnostics, and appropriate remediation ownership.
Use truthful freshness/provenance wording: retrieval is not evaluation, recorded estimates
are not fabricated values, and sources are not limited to searches or SuiteQL.
Apply the existing audience projection to prose, charts, source notes and expandable
evidence. For a requested action, establish its scope, authorization, supported tool schema and business prerequisites; execute only when these are satisfied and verify the resulting state. Keep proposals distinct from completed actions.

## KPI contract
Each card carries label, value or explicit Unavailable/Not measurable, unit/currency, period, scope denominator, source/calculation, native versus computed state, freshness and limitation. A comparison needs a compatible prior snapshot and baseline/target definition.
Good examples: “7 overdue leaf tasks / 42 evaluated”; “80 missing hours in validated assignment windows”; “Actual margin, EUR, recognized basis”; “5 / 5 declared searches completed; 1 unavailable”.
All numerical examples in this reference are synthetic design illustrations, not NetSuite findings.
Do not show a financial card when scope/currency/basis is incompatible. Never substitute hours for cost, invoices for recognized revenue, or a status count for classified risk. Separate findings count, affected-project count and coverage count.
Use source-appropriate precision and units; retain exact values in supporting tables. Expose the numerator/denominator for rates. No overall health score without a configured formula and complete inputs.

## Visual selection
| Question | Preferred view | Evidence requirement / common trap |
|---|---|---|
| Which projects need attention? | Sorted horizontal bars plus compact project table | Count distinct projects separately from findings; include unknown coverage |
| How do dates compare? | Milestone timeline or baseline/current dumbbell | Recorded dates only, baseline version and effective due-date basis |
| What changed over time? | Line or step chart | Comparable historical snapshots; no invented trend from one point |
| Actual versus approved budget? | Paired bars or variance bars | Same period/currency/accounting basis; display commitments separately |
| Where are capacity gaps? | Resource/time heatmap with numeric labels; capacity-demand bars | Same resource/time grain; mark unknown calendars, do not use red as sole cue |
| What is the backlog? | Aging bars and owner/action table | Explicit aging clock/status; no fabricated SLA |
| How do revenue/cost values reconcile? | Waterfall only if components fully reconcile | Otherwise use a reconciliation table with unmatched amount |
| What is risk coverage? | Labeled count bars or matrix | Distinguish Verified/Not verified/Not applicable/Unavailable and unresolved |
| Which dependency matters? | Small linked-record diagram or dependency table | Only supported edges; label inferred links and shared cause separately |
| Which person is eligible? | Evidence table, not a “best employee” score | Exact recorded employee role and date-matched plannedwork capacity; price may be displayed, ranked only on request |
| What needs action now? | Action cards with state and source | A proposal is not a live executable control |

Prefer comparison bars over decorative gauges/donuts; avoid 3-D, chart clutter, unrelated mixed scales and ordinal-severity averages. Bars start at zero unless a clearly justified alternative is labeled; a line-chart range may focus on change with its axis clearly shown. Keep dimensions/time ordering consistent.
Do not make probability-impact heatmaps without validated probability/impact inputs. A severity-by-project matrix is not a probability model.

## Actionable card contract
Title; observed “Risk / trigger:” or operational condition; impacted project/task/window; supported current exposure; proposed next step; recorded owner or “owner not recorded”; due date only if recorded (otherwise proposed and labeled); evidence/source; required authority; execution state; and recheck condition.
Offer local Explain, Show evidence, sort/filter and Plan next steps controls only. For a requested action, establish its scope, authorization, supported tool schema and business prerequisites; execute only when these are satisfied and verify the resulting state. Keep proposals distinct from completed actions.
On follow-up, preserve the card snapshot envelope and route to its domain owner. Show changed/stale evidence before materially different advice. After an action, show verified read-back separately from any pending native indicator refresh.

## Accessible design and honest fallbacks
Use text labels or symbols in addition to color for every state. Preserve native Green/Yellow/Red labels, but use a neutral labeled state for missing/unmeasurable data. Keep risk severity and native status in separate columns/legends.
For authored interfaces, meet at least 4.5:1 normal-text contrast, 3:1 large-text and meaningful non-text contrast, keyboard order/visible focus, descriptive headings, and nondecorative-visual text alternatives. Provide a readable data table alongside each chart. Do not claim conformance without testing the actual rendered output.
Use a logical reading order, plain language and concise titles stating the question answered. Do not rely on hover for essential facts. Test zoom/reflow and narrow screens when creating a real artifact.
When rendering is unavailable, return the same hierarchy using markdown sections/tables with explicit states and sources; do not fabricate clickable widgets, charts, downloadable files or automated refresh.

## Research basis and design choices
Preserve the v1 sourced design choices. See sources.md for retained provenance and official references. The optional small-card selection and the specific card schema are this suite's design choices, not claims of a universal standard.

## Separation required in staffing views
Show native Project Resource Coverage status/message/gap/window separately from ordinary plannedwork utilization/date/capacity.
Use independent legends and labels; never rewrite native Red because ordinary utilization is low.
Show native freshness and known evaluation window, not a fabricated refresh.
Render all requested parts in original order. An incomplete section cannot disappear behind an executive summary.
