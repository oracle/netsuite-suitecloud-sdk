# Shared Dashboard and Export Notes

Use with the shared design guide and domain-specific evidence requirements.

## Composition

Keep the main finding visible first. Use a compact Ocean header and flat portlets on the light page. Place relevant KPI cards across the top, the principal trend/comparison next, then drivers and record detail. Four to six KPIs is a useful dashboard target only when all are relevant and supported; do not manufacture values or comparison periods to fill a row. A smaller request can use one chart or a concise answer.

Keep exception callouts compact and clearly labeled. Put period, subsidiary, currency/book, source time and preliminary/limited status where they matter. Include concise methodology and permitted supporting detail. Use the same verified population across charts and tables unless differences are explicitly explained.

Use real filter/download/collapse controls, with accessible labels and visible focus. Local filters may alter displayed rows or the dashboard population according to the owning domain's contract. Explicitly show which totals remain fixed. A new root scope may require new upstream analysis; the renderer cannot silently expand it. In particular, retain project-reporting evidence, completion and audience gates.

## PDF and presentation design

Use print styling that preserves the current view, exact values, scope and limitations. Hide export/navigation controls, retain chart aspect ratios and plan page breaks at small cards/sections. Avoid clipped text, isolated headings, stretched charts and mostly empty pages. Inspect rendered pages.

When PowerPoint is requested, use the supplied approved template masters/placeholders and artwork, suitable chart images, and editable KPI/table/notes where supported. Preserve classification based on the actual intended audience; an inherited template footer is not evidence of classification. Never approximate logos or assume a viewer has a font installed.

Export values must derive from the same authorized presentation data and current filter state as the screen. Keep all final/preliminary/limited labels, citations and material limitations. An export menu is appropriate only when the active renderer implements those outputs. The shared static helper does not acquire PDF/PPT capability merely by adopting these notes.

## Delivery checks

Check data correctness, mechanics, visual inspection and host support separately. Test the exact delivered HTML and exports, including meaningful filter states. Record skipped validation/render steps explicitly; a mechanical PASS with warnings is not full visual approval. Do not claim that values are visible merely because they occur in hidden/script text. Review keyboard use, long labels, nulls, negative values, desktop and narrow screens, and print previews. Provide an equivalent factual answer when the requested display cannot be produced.

## Traceability and truthful interaction

Apply [source links](../contracts/LINKS.md) and [evidence/scope](../contracts/EVIDENCE.md). Link relevant report/search sources or supporting records where destinations can be established, including a source with no returned transactions. Do not use a broad “record links unavailable” statement to skip available report navigation. Every navigation element must open its stated destination; every local details control must expose real detail with keyboard access. If a function is unavailable, explain it plainly without presenting an active control.

Show current snapshots separately from period results. Unknown close evidence means completion is not established, not that an operational blocker is confirmed. Preserve any required analyst handoff, its producer/reference and status; the visualization must not self-certify it. Retain domain-specific disclosure and export gates. These shared conventions do not introduce an analyst dependency or mandatory PDF/PPT export into unrelated runbooks.

A filter must update dependent KPIs, charts, tables, narrative, source detail and exports together. Explicitly identify intentionally fixed root-scope context. For a view with no applicable measures, hide the irrelevant chart or show a concise empty explanation; do not retain unrelated claims. Maintain exact values and equivalent text without repeating the whole dashboard in the delivery message.

## Output review checklist

- Check each supplied destination is an actual hyperlink with the intended label and row/source association; no placeholders. Check local fragment targets exist. Validate URL safety and derivation separately from live access.
- Exercise each distinct filter/control path and confirm screen, narrative and exported scope agree; testing only the default view is insufficient for an interactive delivery claim.
- Inspect narrow and desktop layouts, keyboard operation, null/zero states and requested export proofs. Preserve material limitations and useful source references in exports; when the format supports clickable links, verify they survive, otherwise include readable source references/URLs.
- Record package, host loading, renderer mechanics, visual inspection, model behavior and account correctness separately. A successful export check does not validate financial facts. Record skipped checks honestly and apply the selected runbook's delivery gate when required checks are unavailable.
- Keep business delivery concise: artifact link, purpose and material limitation. Detailed review receipts and technical diagnostics belong in requested QA material.
