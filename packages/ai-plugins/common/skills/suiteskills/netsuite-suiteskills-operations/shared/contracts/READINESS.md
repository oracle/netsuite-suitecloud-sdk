# Operation-specific capability readiness

Inspect the current callable schemas needed for the selected operation. Packaged tool names and catalogs are helpful starting points, not an exhaustive list, fixed call sequence or proof of current access. Missing tools affect only the dependent operation; discover suitable independently supported alternatives when useful.

## Session context

Reuse trustworthy current account/environment, user and role context. For requests such as “my open cases” or “my pipeline,” use available session identity and the appropriate ownership relationship before asking for a name or searching a directory. Clarify only a material identity or relationship ambiguity. Session identity does not itself establish ownership of every matching record.

When relevant identity, features or preferences are missing, use an available authorized session-context capability. Retrieve only what the request needs and avoid repeating the full payload. Reuse evidence within its applicable account, role, session and scope; refresh after a change, signs of staleness, or when a needed dependency is not established. No session-context tool is a universal prerequisite for unrelated work.

Distinguish listed, successfully called, denied, unavailable and not observed. Incomplete enumeration is not proof of absence. A Connected label does not establish permissions. A verified disabled feature affects its dependent path, not the existence of the whole business process.

## Choose the applicable interface

Record metadata describes record operations; SuiteQL metadata describes query fields and relationships. Use the metadata appropriate to the intended interface. Record metadata is not an extra prerequisite for a SuiteQL request. A REST-only permission error does not by itself establish that independently exposed query access is denied. Keep the same account and role, establish the alternative interface's own access and schema, and respect actual record/field denials and connector policy across paths. An alternative is not permission to evade an access restriction.

A missing create tool does not block reads or local previews. Missing rendering/file capabilities call for another supported format or useful text. Do not claim an artifact or operation was completed when it was not.

## Efficient progress

Plan scoped retrieval in practical batches, reusing relevant current evidence. Complete requested populations using supported pagination and actual tool limits; disclose incomplete coverage. Use a bounded retry for transient read failures, but do not repeat permission or validation failures without a relevant change. For a requested action, establish its scope, authorization, supported tool schema and business prerequisites; execute only when these are satisfied and verify the resulting state. Keep proposals distinct from completed actions.

No account calls are needed merely to list host-exposed tools. Avoid broad capability probes unrelated to the task. Requested scoped reads and local analysis do not need a second go-ahead. Qualification status records what was tested; it is not an execution-disable flag.

## Check the dependency that the next read needs

Before a feature-dependent query, reuse current account/role evidence or inspect an available authorized session capability such as ns_getSessionInfo when its actual schema provides the relevant feature or permission. Check exact dependent report, record type or installed component through supported discovery. No named context tool is universally required. A missing flag or omitted permission is unknown, not disabled or denied. Explicit disabled evidence, access denial, unavailable tool, empty data and unknown readiness have distinct outcomes. Do not issue a known-inapplicable query just to rediscover a disabled feature. Preserve independent supported sections and explain the affected prerequisite; do not install, enable or change access.
