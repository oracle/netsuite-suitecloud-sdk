# Service-report templates

Read the requested mode only. Use the [report access rules](index.md#netsuite-access), [source policy](../../references/service-reports/source-index.md#source-policy), and linked references for that mode. Template preparation does not authorize publication or activation.

## Draft or revise an HTML preview

Use this mode to create, convert, rebrand, or revise a local HTML design. For a NetSuite-backed report, use [account discovery](../../references/service-reports/account-discovery.md#make-one-focused-discovery-pass). Read [source conversion](../../references/service-reports/source-conversion.md) for supplied PDF, SSRS/RDL, HTML, or images, and [Mobile tabs](../../references/service-reports/mobile-tabs.md) when configured tabs determine content. The [HTML starter](../../assets/service-reports/report-preview-starter.html) is optional; it does not set the design.

1. For a NetSuite-backed report, identify the account, report type, content, and selected Field Service Configuration. A local preview can use supplied evidence and fictional values without an account; its account-specific branding and bindings remain unverified. Use the active configuration unless the user names another. Discovery establishes the relevant report data contract, event fields for tab selection, and company or subsidiary branding. Use stored settings and merged Configuration Preview when available through MCP or supplied by the user. In delegated work, the configuration agent provides this snapshot. The template agent may start a fictional placeholder layout and unresolved manifest while discovery runs; account-specific branding and bindings remain unverified until resolved.
2. Follow the supplied template or visual direction. Otherwise, use readable typography, clear hierarchy, consistent alignment and spacing, sufficient contrast, restrained colour, and reliable page breaks. Preserve legally meaningful source footer text unless a change is requested. Use company details, colours, and logo verified through MCP. When no usable logo is available, use a neutral placeholder and mark logo rendering unverified; never invent branding.
3. Create standalone semantic, print-oriented HTML with local CSS and assets. Use obvious fictional customer, address, date, time, inventory, expense, signature, and repeated-row values. Size image placeholders realistically; do not fetch Task media to fill them. Mark dynamic elements with stable `data-field` attributes and repeated groups with `data-repeat`. Identify effects that BFO cannot reproduce.
4. Maintain the [field manifest](../../references/service-reports/account-discovery.md#field-manifest), including empty-label and reserved-space choices. Preview values do not verify bindings. Read a Task's saved values only for an explicitly requested data-filled preview or to verify a binding; related rows and media stay within that scope.
5. Open the HTML in the host's rendered side-browser preview or HTML artifact viewer when supported. The coordinator opens it in the user-facing host during delegated work. Use a local file URL, an available local preview facility, or the selected cloud environment's artifact storage; do not build a server script or application solely for the report. Keep the preview open without remote report assets or NetSuite navigation. If rendered HTML cannot be displayed, explain the limitation; source code or screenshots are not the default substitute. Share HTML source only when requested.
6. Apply feedback to the same HTML and assets. Reload the rendered tab through available browser controls and check long text, empty values, repeated rows, page breaks, and image sizes. If reload control is unavailable, tell the user a manual refresh is needed. Update the manifest for content changes. A purely visual revision needs no new NetSuite query or regenerated XML.

Deliver the rendered preview and current manifest. A preview-only assignment needs neither XML nor a publication proposal. Keep the editable HTML for [XML preparation](#prepare-xml-from-an-accepted-design). Local HTML establishes layout, not NetSuite PDF rendering.

## Prepare XML from an accepted design

Use this mode for an accepted new HTML design. A targeted current-report change uses [edit existing XML](#edit-existing-xml). Read [field resolution](../../references/service-reports/account-discovery.md#resolve-fields) and [NetSuite XML/BFO](../../references/service-reports/netsuite-xml-bfo.md), including its relevant linked documentation, before writing XML. Read [Mobile tabs](../../references/service-reports/mobile-tabs.md) and its relevant documentation only when they affect bindings. The [XML starter](../../assets/service-reports/report-starter.xml) is optional.

1. Start with the latest editable HTML and manifest. For a supplied source without an HTML design, first [draft the preview](#draft-or-revise-an-html-preview). Confirm the chosen Task, Case, or Project Task report contract; another report family's bindings cannot establish it.
2. Resolve every dynamic element under the [field-resolution rules](../../references/service-reports/account-discovery.md#resolve-fields) and [manifest contract](../../references/service-reports/account-discovery.md#field-manifest). Metadata and AI descriptions nominate fields; actual mappings and data verify them. Identify unsupported or unresolved bindings. Do not invent a runtime source or assume Mobile display values are persisted.
3. Translate the current HTML to FreeMarker/BFO XML, preserving section order, labels, proportions, empty-state spacing, and branding intent. Replace unsupported HTML/CSS. Keep bounded blank cells or rows for sections intended to remain visible without data; empty collections alone do not make them conditional. Bind only verified fields, repeats, conditions, and renderer-accessible File Cabinet media. Prepare the smallest configuration patch for required report data or the template reference using [configuration preparation](../configuration.md#prepare-an-authorized-change). In delegated work, the template agent returns mapping requirements and the configuration agent owns the authoritative patch. Retain both HTML and XML for revisions.
4. Apply the [XML/BFO validation gates](../../references/service-reports/netsuite-xml-bfo.md#validation-gates): source inspection, mock expansion and XML validation when a compatible local engine is available, and a representative NetSuite render when MCP supports the selected path. Keep their results distinct; source inspection, well-formed XML, and an HTML preview do not prove the PDF works.

Deliver the XML, manifest, proposed configuration changes, and validation status. Keep the rendered HTML side preview available when supported; show or attach its source only on request. Continue to [publication](publication.md#publish-the-template-and-prepare-configuration) only for the requested or already authorized exact action and revision.

## Edit existing XML

Use the current XML for a Task, Project Task, or Case report change; no HTML redesign is required. Read [account discovery](../../references/service-reports/account-discovery.md) for the effective configuration and data contract, and [NetSuite XML/BFO](../../references/service-reports/netsuite-xml-bfo.md) with its relevant documentation for source and validation rules. Read [Mobile tabs](../../references/service-reports/mobile-tabs.md) and its documentation only if they affect a requested binding.

1. Identify the report family, account, and configuration. Verify the effective `contents.template` path and retrieve that XML through MCP. If either is unreadable, request the current XML and relevant effective configuration from the user. Supplied XML can support a draft, but its match to the active report and readiness for publication remain unverified until the effective source is established. A reference PDF or starter cannot replace the current XML.
2. Define the change against that source. Use a supplied actual NetSuite PDF or screenshot to establish renderer-specific layout and intended empty-field treatment; HTML need not render identically. Save a separate revised XML and edit the smallest relevant blocks. Preserve unrelated content, bindings and guards, repeated-record scope, translations, and logo fallbacks. In Case reports, retain task-linked content within the appropriate task loop. For locale-specific wording, identify the translation mechanism rather than replacing a translation key with a literal label.
3. Verify each added or altered dynamic value under the [field contract](../../references/service-reports/account-discovery.md#resolve-fields). Leave unsupported mappings unresolved. Record a minimal path-level configuration diff against verified effective values only when needed, following [configuration preparation](../configuration.md#prepare-an-authorized-change).
4. Review the XML diff for unintended changes and apply [XML/BFO source and validation rules](../../references/service-reports/netsuite-xml-bfo.md#validation-gates). With a compatible local renderer, expand synthetic missing, populated, repeated, and long-value cases, validate the expanded XML, and inspect the draft PDF. Label an illustrative local preview as such. Record the target-account render still needed; local validation does not establish that result.

Deliver the revised XML, concise change summary, affected mappings and any configuration diff, and validation status. Continue to [publication](publication.md#publish-the-template-and-prepare-configuration) only for the requested or already authorized exact action and revision.
