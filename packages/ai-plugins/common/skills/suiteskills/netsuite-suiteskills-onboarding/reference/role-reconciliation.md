# Role and capability reconciliation

The user's stated work determines relevance. Current evidence establishes only the capabilities it actually observes; it does not establish a job, seniority or consent. A role name and a successful metadata call do not prove access to all data or to writes.

| Observation | Interpretation |
|---|---|
| Current supported operation succeeds | That operation worked within its observed scope and role |
| Explicit permission denial | Stop that denied path; identify the supported access handoff |
| Empty successful result | No returned records within the query's actual coverage; not necessarily absence everywhere |
| Timeout, server error or missing metadata | Capability remains inconclusive; preserve the exact limitation |

Do not probe many record types to profile the user. Use current evidence collected for the requested workflow. Describe a mismatch briefly when it matters: “You mentioned payments; this role's payment capability is unverified. We can start with the supported bill review.” Offer that alternative; wait for selection unless already authorized.

If permissions are broader than the stated job, stay with the stated goal. If narrower, do not invent an administrator fix or infer an entire work area is unavailable from one failed operation. Name only the evidenced gap. A changed account or role requires revalidation of dependent account facts; it does not erase the user's chosen goal.

Define terms where used: general ledger is the accounting ledger; receivables are customer amounts due; payables are vendor amounts due. Chief executive, chief financial and chief operating officers are examples of an executive remit, not required role names. Technical identifiers in tool schemas retain their actual spelling.
