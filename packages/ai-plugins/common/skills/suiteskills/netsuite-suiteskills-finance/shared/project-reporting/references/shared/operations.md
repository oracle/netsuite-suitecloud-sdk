# Domain reference

Support the user’s requested analysis and authorized actions through available, supported tools. Establish the target, intended effect and required business inputs before acting; reuse authorization already given for that exact scope. Tool availability and source examples do not grant authorization. Preserve business validation, actual host approvals and account permissions. If the operation or required procedure is unavailable, explain the specific gap and provide a useful proposal without claiming execution.

# Project Operations
Own work queues, exact-user tasks/priorities, time capture, staffing, ordinary utilization and supported project actions.
Read resource-identity-and-scope.md, plannedwork-and-native-risk.md, horizon.md, placement.md and project-indicators.md before relevant analysis.
Participate in the broad root evidence-led investigation or the focused derived searches required by a narrow request. A facts_only child supplies evidence without restarting native intake or the root plan.

## Work and identity
Resolve session identity exactly; list personal work only via verified assignment/approval-routing references.
Separate owned tasks, project-manager responsibilities, approval queues, others' responses and unassigned work.
Use incomplete executable leaf tasks and validated effective due dates. Keep today's deadlines separate from overdue.
Preserve exact recorded priorities; advisory sequencing can use evidenced due/overdue/blocker obligations but is not a invented score.
A Red project does not automatically assign the user an action. Counts do not rate employee performance.
Approvals use actual workflow routing, not supervisor/project-manager labels. Distinguish open, pending, rejected and approved time.
Missing time needs expected hours/leave/exception definitions, not absence of visible records.
Keep meeting-specific actions tied to actual notes/action records; ordinary tasks alone do not prove a meeting commitment.

## Staffing sweep
Before staffed/available claims, enumerate remaining/planned leaf work for missing assignment, generic, inactive/ineligible assignee,
early-ending assignments and assignment-level missing hours. A filtered native positive-gap dataset is not the entire staffing inventory.
For remaining-work risk read native -9 first, preserve it even without daily plannedwork, then validate its gap/assignment/window.
For ordinary demand use only plannedwork; retain all other authorized commitments of the same resources in the same dates.
No allocation rows and no plannedwork rows are distinct statements; neither proves availability without complete sources and calendar/leave.
Report same-day conflicts before aggregate averages. A positive net weekly balance does not make an unavailable required day usable.

## Placement and pipeline
Default to employee Project Resources with the exact recorded role; retain vendors/contractors in existing-work analysis, not default candidates.
Only broaden candidates on explicit instruction. Use date-matched capacity. Display permitted rate facts; price filters/ranking require explicit request.
Track proposed consumption per resource/day across multiple recommendations so the same capacity is not promised twice.
Identify pipeline records through discovered relations and user/configured inclusion criteria; keep tentative and committed work separate.
Do not fabricate probability, win date, or weighted demand. Capacity effects require documented plannedwork.
Use neutral order without unsupported reputation/reliability/skill inference.

## Planning and authorized execution
Use sow-to-project.md for SOW drafts or creation. A draft or suggested decomposition is not an agreed plan.
For requested task changes or assignments, apply the shared action contract. This reference supplies analysis context, not a complete account-action procedure.
Allocation records are not created or changed as an implicit planning step. If the account requires an allocation prerequisite for an assignment,
surface that prerequisite and pause that write; do not silently add allocation planning or bypass permissions.
Financial transaction actions remain outside this suite. Supported project actions are not refused merely because they write data.

## Present
Use presentation.md: scope/as-of/windows, request-order answers, factual work tables, plannedwork/capacity views, separate native coverage cards,
date-specific placement facts, limitations, and action states. Gate completion; do not claim an unsupported artifact or refresh.


## Proposal handoff

The Statement of Work (SOW) execution runbook is not included in this distribution. Retain proposal facts for financial/risk analysis; a requested SOW action needs an applicable supported procedure and tool.
