# Domain reference

Support the user’s requested analysis and authorized actions through available, supported tools. Establish the target, intended effect and required business inputs before acting; reuse authorization already given for that exact scope. Tool availability and source examples do not grant authorization. Preserve business validation, actual host approvals and account permissions. If the operation or required procedure is unavailable, explain the specific gap and provide a useful proposal without claiming execution.

## Trigger and ownership
A broad review, comparison, multi-item analysis, or substantive risk review must use
this workflow. Broad review of one project also qualifies. Do not classify breadth
solely by entity count, a question keyword, or a fixed list of prompts.
One named item with one noncomparative factual lookup may use concise text/table. This changes presentation
size, not applicable evidence, identity or risk requirements.
Explicit text-only requests are honored with the same permitted evidence coverage.
Operations owns work/capacity/SOW facts; Financial owns monetary meaning; Risk owns
risk classification; Health owns combined portfolio synthesis. No fifth skill.

## Ordered evidence plan
Resolve actual requested obligations, full authorized project/resource populations,
exact user and manager identities, date windows/timezones, financial context and
available capabilities first. Preserve every original obligation and its requested order.
Compile `review_depth.plan` into `request.review_plan` BEFORE retrieval; include it in
the original request signature. Select actual domain families, not a question catalogue.
Do not remove a family to excuse missing evidence. Broad Health/Risk reviews include
task-schedule and whole-scope task-effort stages even when only header data are easy
to obtain. Operations may select work or staffing or both for the actual question.

Attempt all applicable native Project Indicators first. For staffing risk, explicitly
prioritize Project Resource Coverage for Remaining Work using the runtime-validated
type mapping; never assume a tenant-specific ID. A native failure starts documented
alternatives, not a Green result. Then complete required detailed evidence:
- Delivery: task/subtask hierarchy, executable leaves, exact completion meanings,
  effective due dates, aging and supported dependencies, not just job headers.
- Effort: compatible task AND project plannedwork/actual-time comparisons, including
  completed work when in scope. Do not equate actual time and allocated time.
- Staffing: complete resource directory including vendors/contractors and zero-work
  resources; assignments, dated plannedwork, calendars, approved leave and competing
  commitments. Allocations may diagnose native risk, never ordinary utilization.
- Financial: relevant transactions/lines or compatible detail reports, nonoverlapping
  project attribution, currency/book/period/basis and reconciliation to the observed
  total; applicable billing/expense/domain rules. Do not rebuild total actual cost
  from billing rates or labor time alone.
- Risk: the complete declared evidence-led investigation for every scoped existing
  project, after native intake and the supporting evidence. Co-occurrence is not
  confirmed scope cause, causation, higher severity, or critical path.
- Source-only SOW: use the source obligations, plan version, approvals and reconciliation
  contracts. Do not invent native indicators or existing projects for a draft.

Suitable standard detail reports/searches may supply record-grain evidence. This is
a granularity requirement, not a raw-API/SuiteQL mandate. Preserve the connector's
tool-discovery, permission and query-approval rules. Reuse compatible source evidence
within one root review; a layout-only follow-up does not repeat the account sweep.

## Machine contract and completion
The plan records profile/domains, context and obligation digests, and ordered stage
specifications with grain, required fields, permitted normalized input paths and exact
expected member lists. The original request signature binds this plan.
`result.review_depth` records version, plan digest, one ordered row per stage and an
empty remaining_stages list only when work is actually complete.
Each row supplies the exact requirement, actual phase sequence, state, source refs,
inherited source-check fields, disjoint evaluated/unavailable/not_applicable/unresolved
member partitions, limitations and record-level detail proof.
For exhausted stages, detail_proof binds the actual normalized input digest, row count,
grain, verified fields, complete population and reconciliation to summaries. Whole-scope
effort requires explicit includes_completed_work proof; an overdue subset is insufficient.
Positive empty-result evidence must establish all scoped zero-row members; do not infer
absence from an empty join or count. Unknown definition/population is not zero.
For unavailable stages, keep the exact missing inputs, attempted authorized channels,
errors, exhausted alternatives, remediation and responsible role. An available untried
channel or pending authorization remains unfinished. Not-applicable needs positive proof.

`review_depth.evaluate` wraps the unmodified completion_gate and risk_gate. It rejects
missing/extra/reordered/changed stages, pending work, unreconciled member counts, stale
detail digests, absent record detail, unverified grain and incomplete pages/periods.
It verifies declarations, not source authenticity or host call timing. The host must
authenticate scope, source traces, authorization and chronology; hashes are not proof.
A complete review may retain exhausted unavailable stages: label it LIMITED, never
complete assurance. Verified header facts may remain explicitly labeled observations,
not a completed detailed review. Show missing stage names even if no data panel exists.

## Dashboard default and fallback
After gates, default to a graphical dashboard for substantive multidimensional findings, including follow-ups; allow only complete one-fact single-sentence exceptions. Prefer actual host
inline tools when supported; otherwise deliver portable HTML. An unsupported inline
tool does not imply an HTML artifact is impossible. Use review_delivery.py with actual
host capability flags and a separately authenticated publication policy.
Normally select 3–5 relevant cards and 1–2 domain-appropriate charts, synthesized
Confirmed/Interpretation findings, a prominent coverage callout, exact detail and sources.
Do not invent measures to fill slots. Expected unavailable measures remain unavailable.
Keep the same requested answers in original order within the audit detail; a top chart
does not truncate the full scope. Counts are not severity.
Use table/text fallback only for unsupported delivery, a visual that would misrepresent
the evidence, or an explicit text-only request. State the specific reason. Preserve every
audience-permitted row/value/source and limitation, using continuation/detail as needed.
An incomplete review may still have an honest limited dashboard. A privacy failure
blocks publication in EVERY format; it is not a reason to leak the data as Markdown.

## Privacy and asset boundary
Protected domain evidence and executable/approved SOW objects never become arbitrary
rendered JSON. Apply account-neutrality-and-disclosure.md to charts, narrative,
captions, diagnostics, tooltips, expandable evidence and fallbacks.
Reusable files contain no live account records, private URLs, fixed tenant mappings
or historical personnel examples. Runtime evidence stays outside the release directory.
Keep only maintained CSS/JS and blank SOW output templates under assets. Synthetic
development factories generate example artifacts OUTSIDE the edition and imports.
Configuration/allowlists live under visual-config in shared references; do not delete
privacy controls or business evidence just to reduce installed size.
