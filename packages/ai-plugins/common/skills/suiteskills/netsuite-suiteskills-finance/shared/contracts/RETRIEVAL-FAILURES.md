# Retrieval failure decisions

Load after a source failure or when population completeness is uncertain. Preserve the actual operation, exact returned evidence and affected scope. Do not infer an error class from an empty result alone.

| State | Evidence needed | Next action |
|---|---|---|
| `role_denied` | Explicit permission/access denial applicable to the selected operation | Stop the denied operation and explain the access limit. Do not switch identities or bypass the denial. Distinguish an interface-only permission failure from a record/field restriction using READINESS; an independently authorized source may still answer the request in the same role. |
| `connector_restricted` | Explicit connector policy/catalog restriction | Stop the affected metadata-dependent SuiteQL branch. Do not label this a role denial, missing table or absent business records. No packaged-schema, remembered-schema or trial-query bypass. |
| `schema_unavailable` | Failed, missing, empty or insufficient current metadata for any required table/field/join | Pause the query dependent on the missing evidence. Establish that evidence through an appropriate supported path or the selected runbook's applicable bounded validation procedure; do not guess. Record metadata alone is not SuiteQL metadata. |
| `source_incomplete` | Hidden/unverified filters, unknown grain, missing pages, duplicates, missing periods, unconfirmed populations or unreconciled totals | Keep observed values qualified; use `partial` or `blocked` according to whether a useful scoped result remains. Never fill unknowns with zero or claim complete population. |
| `server_failure` | Explicit service/transport failure without evidence of a permission decision | Record the failure without claiming denied access, absent data or an empty result. A bounded retry of the same read may be useful; repeated unchanged failure stops the branch. |

When the class is uncertain, report `unknown` with the observed error and affected branch. Do not fabricate classification certainty.

## Independently qualified alternatives

An alternative source needs its own access and the source identity, scope and semantics relevant to the requested conclusion. Establish filters, grain, period/date basis, book/currency and completeness where they affect that conclusion; a simple record lookup does not need unrelated accounting checks. It does not inherit qualification from the failed branch. Native report summary values do not supply transaction detail. A saved-search result does not reveal all hidden criteria by itself. A direct-record read does not prove a population.

For metadata-dependent SQL, establish current query-schema evidence for each required table, field and relationship through the available metadata interface, reusing still-applicable session evidence. Respect actual tool requirements and access denials. If a dependency remains unknown, use an applicable bounded validation procedure documented by the selected runbook or another independently supported source; do not guess SQL. For paged retrieval, follow the current interface's page or continuation semantics, stable ordering and distinct keys. In an interface using zero-based `pageIndex`, it is a page number, not a row offset. Use returned counts/continuation where available and retrieve the pages required for the requested coverage; field names here are examples, not prerequisites for different supported interfaces. Saved-search range semantics must follow its own current tool schema/observed response; do not transpose SuiteQL pagination rules.

If no trusted source remains, ask for the specific missing report/search or approved extract needed to continue. If useful, provide an analysis outline in conversation or the requested artifact. For a requested action, establish its scope, authorization, supported tool schema and business prerequisites; execute only when these are satisfied and verify the resulting state. Keep proposals distinct from completed actions.
