# Current customer credit analysis

Use this workflow after the time-frame gate in `SKILL.md` establishes today's current records, either explicitly or by default for an undated request. It covers portfolio coverage, limit exceptions, signed overdue exposure, and a customer follow-up shortlist. Historical requests belong to a separate reporting workflow.

## 1. Fix the requested basis

Record the current retrieval date/time and established time zone, accessible subsidiary scope, requested customer population, currency basis, hierarchy treatment, exposure definition, and approaching threshold. When no date or narrower scope is supplied in the request or relevant conversation, default to all role-accessible customer records today and state that basis without asking for confirmation. Respect explicit dates and narrower filters under the time-frame gate. Use an analytical 80% threshold unless the user supplies a threshold or an applicable verified policy threshold is available. A current record is a current snapshot; it does not prove its balance on a prior date.

## 2. Read a complete minimal population

1. Establish current SuiteQL metadata before composing a query; separately verify saved-search columns, filters and population before relying on a search. Confirm the identity, active flag, person/company flag, stage, balance, credit limit, currency, subsidiary, and hierarchy fields actually exposed under the role. Candidate field names may include `balanceSearch`, `creditLimit`, `isInactive`, `isPerson`, `searchStage`, `parent`, `topLevelParent`, `consolBalanceSearch`, and `unbilledOrdersSearch`; do not assume every account or connector exposes them.
2. Prefer one unjoined, explicit-field, paginated customer read for a current portfolio. Do not use `SELECT *` or fetch each full record merely to learn balance and limit. Begin with connector-supported pagination; for `ns_runCustomSuiteQL`, inspect the current callable page-size and continuation schema, begin at its supported first page, then follow supported continuation through the final page. A historical page-size example is not a current interface guarantee. Confirm returned row count, unique identities, total results, and whether any page is missing or capped.
3. Apply only the requested population and subsidiary filters. If the request is “all customers,” include accessible inactive, person, Lead, and Prospect rows in the population count and report their breakdown. If the request is “active company Customer-stage,” verify and apply all three predicates. If a required predicate is inaccessible, do not claim that precise population.
4. Classify limits as positive, explicit zero, verified blank, inaccessible, or unparseable. Distinguish a source null from a query/permission omission. Keep negative and zero balances in population counts; do not silently discard credits.
5. Preserve each row's native currency. Compare only a verified same-customer, same-hierarchy balance and limit in that currency. Use decimal arithmetic at source precision; format only for display.

If a governed saved search supplies the same fields, scope, and complete pagination, it is an acceptable source. A governed consolidated total requested as of today requires an appropriate A/R report with verified date, labels, and filters; report it separately and do not substitute a raw customer-record sum. Do not run historical reports in this workflow. If report bucket labels are missing, withhold bucket interpretation.

## 3. Resolve enforcement basis

First check the current session context for **Consolidated Payments**, using the feature-state rules in [account-validation.md](account-validation.md). Record enabled, disabled, or unverified and the source; do not infer the state from consolidated customer fields or an accounting-preference lookup. NetSuite applies the top-level customer's credit limit to the hierarchy when Consolidated Payments is enabled; no separate parent-limit preference is needed for that rule.

Verify **Customer Credit Limit Includes Orders** and **Customer Credit Limit Handling** from the session preferences and an explicit accounting-preference read when available: `SELECT preference, value FROM CompanyPreference WHERE preference IN ('CUSTCREDLIMORDERS', 'CUSTCREDLIMHANDLING')`. This query checks accounting preferences, not the Consolidated Payments feature.

If two verified current feature-state sources disagree, state the conflicting evidence and show only clearly labeled individual-record screens until the feature state is reconciled. The count of calculated exceptions must use the same comparison units as the table: a verified grouped hierarchy counts once; separate parent and child rows count twice. State an underlying customer-row count separately if useful.

- When Consolidated Payments is verified **enabled**, compare the top-parent positive limit with its corresponding consolidated exposure. Retain children in the source population count, show them only as a breakdown of the parent exception, and never add parent and child consolidated balances together.
- When Consolidated Payments is verified **disabled**, compare each customer's own comparable exposure and limit. A child can have its own calculated exception; do not use a parent consolidated balance as its exposure.
- When hierarchy behavior is unavailable, show native **row-level screens** and say the enforcement-level hierarchy conclusion is unverified. Do not call the feature enabled or disabled without source evidence.
- When the account preference includes unbilled orders, show A/R and unbilled orders separately and use their verified comparable sum for the enforcement comparison. When disabled, compare A/R only. When unknown, present A/R-only calculations as such; do not claim an order would warn or block.
- An actual credit hold is a separate record status. Read it only if requested and label it as recorded status, never as a consequence inferred from the limit math. For a claimed hold-status list, inspect `onCreditHold` for every named customer on the same current source basis; do not turn missing or unread values into No, and do not generalize a checked subset to “all others.”

## 4. Calculate and label exceptions

For positive comparable limits:

```text
utilization = comparable_exposure / positive_limit × 100
available_credit = positive_limit − comparable_exposure
over_by = comparable_exposure − positive_limit, only when positive
```

Use source precision: exposure > limit is calculated over-limit; equality is at-limit; threshold ≤ utilization < 100% is approaching-limit; lower values are within-limit. The 80% default is an analytical screen, not a verified account policy. For positive **comparable exposure** with a verified blank limit, use `blank-limit-with-exposure`. For positive comparable exposure with an explicit zero limit, use `zero-limit-with-exposure`. These are separate classes. With an order-inclusive preference, positive unbilled orders can create an exception even if A/R balance is zero. Show A/R and orders separately. Do not calculate utilization or available credit for blank, zero, inaccessible, or unparseable limits.

Keep amounts separated by their verified currency codes. Present each currency's exception amounts under its own heading or in its own table, and sort only within that currency. Do not nominally rank or sum over-by amounts across currencies. For a report-currency screen, a verified NetSuite rate with applicable date and direction can convert either figure into the other's currency: EUR limit → USD exposure currency or USD exposure → EUR limit currency are both valid if the corresponding rate is supplied. Show the rate, direction, operation, and arithmetic utilization. Verify rate type, organizational scope, and matching customer/hierarchy basis before calling the result a NetSuite enforcement exception. If these remain unresolved, label the conversion an illustrative calculation. Never silently invert a rate, use a market rate, or compare raw amounts from different currencies. If no applicable rate direction/date or comparable amount basis can be established, withhold the cross-currency calculation; same-currency customer-record calculations may still proceed.

## 5. Read signed aging with stated coverage

The customer-record overdue measure is `aging1 + aging2 + aging3 + aging4` (or verified corresponding consolidated past-due buckets for a verified parent-enforcement basis). Exclude Current. Preserve negative buckets and the signed result. A negative sum is a net past-due credit, not debt. Do not replace this measure with the separate Overdue Balance field. If both measures are shown, verify equality or compute the exact signed difference at source precision. Do not call equal values different, and do not explain a mismatch as excluded credits, timing, or payment activity unless transaction-level evidence supports that cause. Four aging buckets alone do not prove that the entire remaining balance sits in Current; read a verified Current field before saying so.

Before displaying an aging breakdown, verify the customer-facing labels in direct-record metadata and use those labels in tables and prose, not internal field IDs. For the standard verified mapping, display `aging1`/`consolAging1` as **1–30 Days**, `aging2`/`consolAging2` as **31–60 Days**, `aging3`/`consolAging3` as **61–90 Days**, and `aging4`/`consolAging4` as **Over 90 Days**. Keep field IDs in tool calls or necessary technical evidence. Keep Current separate and preserve each negative amount under its verified past-due label. If the labels cannot be verified, show the signed past-due total without a bucket breakdown and state that the bucket labels are unverified.

`aging1`–`aging4` may be absent from SuiteQL while present on the direct customer-record API. Use current query metadata to determine SuiteQL field support before querying. A separate direct-record path may be used only when its callable schema and applicable record metadata establish the aging fields for the known customer. If no supported direct path exists, report aging as unverified; do not issue speculative calls or generalize an interface failure to the account. Do not claim an account-wide limitation from a SuiteQL error. If direct aging remains unavailable, say the signed overdue review is unverified; do not relabel `overdueBalanceSearch` or `daysOverdueSearch` as the signed measure or use them to rank collection follow-up by default. A negative total A/R balance may coexist with positive past-due buckets, so do not infer that every net-credit customer has no overdue debt.

For a standard portfolio review, directly read the four aging buckets for calculated limit exceptions, at/approaching rows, and positive-exposure blank/zero-limit rows. Deduplicate those customer IDs, then partition **all remaining positive-comparable-exposure rows by currency** and add up to five largest from **each** currency, even when that currency has no exception row. Reconcile the selected IDs to the stated shortlist size before reading and reporting coverage. This is a **review shortlist**. Rank follow-up only among customers with verified aging in a comparable currency. Report `aging-read / full requested population` and `full population minus aging-read = unread`; for example, 20 reads among 406 customers means 386 unread, even if only 19 of 39 positive-exposure customers were unread. A zero or negative A/R balance can still have positive past-due buckets; do not describe any unread row as having no overdue amount. If the user explicitly requests portfolio-wide overdue coverage, read every row in the requested population or state the access, time, or pagination cap and withhold the full-population count and sum.

If a transient rate limit interrupts aging reads, back off and retry only the missing customer IDs once; do not restart the population scan. If any aging reads still fail, report the verified subset and each missing record's coverage as unknown. Do not invent zeros, combine currencies, or use a subtotal as a portfolio total.

## 6. Deliver a concise review

Lead with population and source completeness, limit coverage, threshold source, and the number of calculated exceptions. Show separate compact tables for over-limit, at/approaching, blank-limit-with-exposure, and zero-limit-with-exposure; omit empty tables with a short “none found” line. Include A/R and orders separately when orders are part of the comparison. Include signed overdue only for read records, clearly distinguish net credits, and keep each currency visible. Use an amount order within currency and verified coverage, not an unsupported days-past-due or collections-urgency ranking.

End with the source and material limits: current record versus report as-of date, unread aging population, rate basis, hierarchy and order preferences, and inaccessible fields. Do not prescribe collections actions or propose a new limit without an approved rule.
