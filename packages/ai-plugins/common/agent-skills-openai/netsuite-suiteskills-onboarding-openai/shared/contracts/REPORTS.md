# Report discovery and scope

Use an appropriate report when it supplies the business definition and coverage the request needs. The steps below describe common report-tool capabilities, not an exclusive interface or required call sequence. Reuse current matching discovery results. Use the actual callable schema when names, filters or required inputs differ from these examples.

1. Resolve the requested report by business purpose and observed identity. A capability such as `ns_listAllReports` can provide titles, IDs and scope metadata. Disambiguate duplicate titles; do not infer report type from a negative ID. A missing catalog entry is not an empty report result. Investigate a suitable available report, search or query alternative before declaring the request blocked.
2. Establish relevant date/period basis, subsidiary/consolidation, accounting book and currency. Clarify material ambiguity; reuse choices already supplied. Do not assume the fiscal year begins in January or claim an unsupported filter was applied. A qualified default-scope result can still be useful if it answers the question.
3. Supply the required inputs of the current report interface. For example, an interface may require `dateTo`, conditionally require `dateFrom`, or expose book, nexus and consolidation selectors. Discover actual identifiers and supported dimensions through available metadata or catalogs; do not manufacture IDs. Packaged field names and flag combinations are examples, not a limit on newer supported filters.
4. Use an optional native filter app if helpful and available. Wait for its returned selections and validate them against the report interface. Conversational choices and supported reads can supply equivalent inputs; opening an app does not establish a user selection.
5. Run the report and inspect its actual response. Select measures by verified labels, meaning and hierarchy rather than row position. A summary supplies summary facts; detail or trends require the relevant rows. Do not automatically drop row zero or null-alias rows, double-count parents and children, or infer an expense sign flip.
6. Preserve signs, units, scope and completeness. Null is unknown, and an error is not an empty success. An ambiguous currency symbol remains ambiguous until evidence tied to the report establishes its currency. A subsidiary's base currency alone may not establish a consolidated report's currency.
7. Return useful supported findings with material limitations. Another source can answer the question when its definition, scope, grain and completeness are suitable; disclose meaningful source changes and reconcile differences. Apply [retrieval failures](RETRIEVAL-FAILURES.md) to actual access or service failures and [outputs](OUTPUTS.md) when using the bundled artifact helper.

## Scope continuity and validation links

Apply [evidence and scope](EVIDENCE.md). Preserve the user's selected scope across reports, while distinguishing activity periods, point-in-time balances and retrieval timestamps. A current aging report cannot substitute silently for month-end aging. Multiple same-role sources share the role's visibility limitation. Missing or duplicated column labels require limited interpretation and a precise observation, not an assumed connector root cause.

Retain the report identity and relevant filter evidence for [source navigation](LINKS.md), even when there are no detail rows. Resolve a report/search destination when supported; do not infer it from an API endpoint or fabricate a saved search matching a query. Explain when the navigation URL does not reproduce the applied filters.
